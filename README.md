# LIV Planning

Единая система планирования, фактического учёта и отчётности строительного проекта.

## Текущее состояние

LIV уже использует:

- авторизацию и роли Supabase;
- общую серверную память;
- локальный кэш IndexedDB;
- нормализованные серверные таблицы;
- поэтапную миграцию старого `project_snapshot`;
- импорт Excel/CSV;
- отдельный импорт ключевых дат;
- версии графиков;
- шахматки;
- ресурсы;
- номерные элементы;
- PDF-схемы и отметки;
- прогноз рисков ключевых дат;
- журнал импортов и изменений.

`project_snapshot` временно сохраняется как совместимый резерв. Новые данные параллельно записываются в нормализованную модель Supabase.

## Правильный порядок загрузки проекта

1. Организации, договоры и ключевые даты.
2. Версии графиков и зависимости.
3. Фронты и проектные объёмы.
4. Группы и реестр свай, анкеров и других номерных элементов.
5. Ежедневные факты, ресурсы и планы подрядчиков.
6. Связи со схемами и автоматическая отчётность.

Подробнее: [docs/IMPORT_PIPELINE.md](docs/IMPORT_PIPELINE.md).

## Архитектура

- **GitHub** — код, документация и автоматические проверки.
- **Supabase PostgreSQL** — рабочие данные и права доступа.
- **Supabase Storage** — PDF-схемы и файлы.
- **IndexedDB** — локальный кэш и аварийная копия.

Подробная модель: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Принципы данных

- график, фронт и факт — разные связанные сущности;
- дневной факт является первичным;
- накопительный итог и недельный прирост рассчитываются;
- один фронт может иметь несколько физических показателей;
- номер элемента уникален только внутри корректного контекста;
- новая версия графика не уничтожает предыдущую;
- импорт всегда проходит предпросмотр и подтверждение;
- удаление рабочих данных по умолчанию выполняется через архивирование;
- каждое импортированное значение хранит источник.

## Прогноз ключевых дат

LIV рассчитывает:

- целевой объём;
- текущий факт;
- остаток;
- число производственных дней до срока;
- темп последних 7 и 28 дней;
- требуемый темп;
- прогноз к целевой дате;
- ожидаемый недобор;
- прогноз завершения;
- уровень риска.

## Номерные элементы

Контекст уникальности:

`проект + тип элемента + здание + группа/ярус/марка + захватка + зона + номер`.

Поэтому, например, БСС-1 №93 и БСС-2 №93 либо Г1 №1 и Г2 №1 являются разными элементами.

## Проверка изменений

GitHub Actions выполняет синтаксическую проверку всех JavaScript-файлов и проверяет локальные ссылки на скрипты после каждого изменения ветки `main`.

Проверки импорта КД, PDF, контекста номерных элементов и конфликтов синхронизации: `node --test tests/*.test.cjs`.
`tests/schema-smoke.sql` проверяет ограничения рабочей схемы в транзакции с откатом; он не проверяет браузерную авторизацию и загрузку байтов в Storage.

## Графики: версии и расчёт (16.10.2026)

В разделе «График» доступен импорт Excel/CSV с распознаванием строк зданий,
элементов, захваток и КД. Сначала проверяются все распознанные строки, затем
создаётся тестовая версия. Рабочая версия меняется только после принятия.

Для повторных загрузок задавайте одну группу графика, назначение, организацию
и номер договора. Для отдельных листов по умолчанию создаются разные группы.
Графики Заказчика, договоры подрядчиков и внутренние графики хранятся отдельно.
В сравнении можно выбрать две принятые/архивные версии. Положительное изменение
срока означает более позднее окончание, отрицательное — более раннее.

В расчёте длительности доступны ручные рабочие дни, выработка на один ресурс
и общий фактический темп связанного фронта. Поддержаны календари 7/0, 6/1, 5/2,
четыре типа связей и целочисленные лаги. Начало и окончание рабочего интервала
считаются включительно. Исходная длительность импорта сохраняется отдельно;
при первом расчёте ручная длительность выводится из дат и выбранного календаря.
Прогноз сохраняется отдельной рабочей версией, договорные даты не меняются.

КД можно зарегистрировать в договорном журнале при принятии, указав организацию
и номер договора и включив соответствующий флажок. Рабочий прогноз связанной
КД учитывается в оценке риска без выдуманного физического объёма. Готовность
работы 100% не является подтверждением выполнения договорной КД.

Ограничения этого этапа:
- PDF и MPP не импортируются как структурированный график; используйте Excel/CSV.
- Автоматическое сопоставление использует точный контекст или связанный фронт.
  Укрупнение/дробление и неоднозначные соответствия требуют отдельной доработки.
- Ресурсы постоянны внутри расчёта задачи; выравнивания общих ресурсов,
  праздничных исключений и полного расчёта критического пути пока нет.
- План объёмов за период — явная равномерная оценка по рабочим дням выбранной
  версии, а не замена утверждённой поэтапной разбивки объёмов.
- Шахматка графика — отдельное представление задач выбранной версии. Она не
  заменяет основной настраиваемый модуль шахматок фронтов.
- `saveProject` сохраняет локально и ставит серверную запись в очередь. Перед
  рабочим вводом дождитесь подтверждения серверной синхронизации.

Тесты: `npm ci`, затем `npm test`. Для проверки Excel задайте
`LIV_XLSX_TEST_PATH` с путём к SheetJS 0.18.5. Пользовательские договорные книги
не включены в репозиторий; локальная проверка принимает их каталог через
`LIV_SCHEDULE_FIXTURES`. SQL-проверка `tests/planning-schema-smoke.sql` выполняет
все тестовые записи в транзакции с откатом.

Входящие связи суммарных задач требуют переноса на конкретную работу; расчёт блокируется, чтобы не игнорировать ограничение срока.

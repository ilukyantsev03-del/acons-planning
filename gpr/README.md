# Отдельная страница ГПР

Страница открывается на GitHub Pages по пути `/acons-planning/gpr/`.
Она использует только таблицы `gpr_schedules`, `gpr_items`, `gpr_members` и функции доступа `gpr_role`, `gpr_can_read`, `gpr_can_write`. Она не загружает и не изменяет снимки LIV Planning.

## Доступ

Публичный просмотр определяется `gpr_schedules.public_read`. Поиск, фильтры, масштаб, группировки и отчётная дата работают локально и доступны без входа.

Кнопка «Войти для редактирования» использует существующие email и пароль Supabase Auth. Создание пользователей и назначение прав через страницу отсутствуют. Редактор открывается только при ответе `owner` от `gpr_role`; запись дополнительно защищена существующими RLS-политиками базы. Клиентская конфигурация содержит только публичный publishable key.

Вход по паролю не требует добавления страницы в Redirect URLs. Вход по письму в этой версии не используется. Сессия страницы хранится отдельно от сессии LIV (`gpr-auth-v1`).

## Данные и сохранение

`gpr_items`: `schedule_id` — ID графика, `kind` — `task`, `stage` или `meta`, `id` — локальный ID, `data` — JSON, `version` — версия записи. `meta/settings` содержит название, начало проекта и срок сдачи. `meta/baseline` содержит дату фиксации и словарь `items: {taskId: [start, finish]}`.

Задача: `id`, `stage`, `name`, `order`, `num`, `dur` (календарные дни), `cons` (начало не ранее), `preds: [{id,type,lag}]`, `unit`, `vol`, `open` (начальный накопительный факт), `facts: {YYYY-MM-DD: quantity}`, `contractor`, `note`, `ms`. Типы связей: ОН, НН, ОО, НО. Поле `ms` обозначает веху. Этап: `id`, `name`, `short`, `order`, `note`.

Работы и связи не встроены в публичные исходники. При загрузке выполняется проверка идентификаторов, существования этапов/предшественников и циклов. Обновление и удаление используют условие `version = ожидаемая_версия`; конфликт не перезаписывает другую редакцию. Записи одного элемента выполняются последовательно. Сохранение нескольких строк не является одной транзакцией: при частичном сбое подтверждённые записи сохраняются, ошибка показывается пользователю, остальные изменения требуют повторной проверки. Историю записывает существующий серверный триггер в `gpr_history`.

Экспорт JSON и CSV сохраняет файл пользователю. Импорт и локальная подмена графика через страницу отключены. Новые графики добавляются в базу отдельно и появляются в списке после обновления страницы.

## Проверка

1. Без входа открыть страницу: список графиков, таблица, Гант, фильтры, группировки и карточка доступны; поля карточки отключены.
2. Без входа попытка записи должна отклоняться RLS независимо от состояния кнопок.
3. Войти существующим аккаунтом владельца: появляются редактирование, добавление, порядок этапов и базовый план.
4. Изменить тестовую работу, обновить страницу, сверить сохранение. Повторить изменение из устаревшего окна: должна появиться ошибка версии.
5. Выйти: редактирование закрывается; публичный просмотр остаётся доступен.

Локальные проверки: `node --check gpr/app.js`, `node --check gpr/store.js`, `node --test gpr/store.test.cjs`.

SDK Supabase JS 2.49.1 включён в `vendor/`; исходный пакет: `@supabase/supabase-js`, лицензия MIT. Ключи service_role и секретные ключи использовать в этой папке нельзя.

## Мокап — Блок 2

`mockup.html?schedule=mockup-block2` — отдельный профиль. Основной фасадный экран только направляет выбранный профиль на эту страницу; его расчёт и данные не изменены.

- Текущие задачи и вложенные сводные группы хранятся в `gpr_items`, профиль `meta/settings.profile=mockup`.
- Даты/время и базовые даты MPP сохранены отдельно. Календарь: 1200 минут/день, интервалы 01–11 и 13–23, семь рабочих дней, исключения из MPP. Импортированные сроки при загрузке не пересчитываются. Для редактирования используются рабочие минуты. Фактическое начало фиксируется: сдвиг предшественника не переписывает состоявшийся факт.
- Готовность сводных строк — средняя по несводным потомкам (Number1 в MPP), без взвешивания по длительности. При заданном объёме готовность работы считается из накопительного и дневного факта.
- `gpr_mockup_save` — SECURITY INVOKER RPC, применяет пакет изменений, проверяет ревизию и циклы, сохраняет архив состояния в одной транзакции. Запись только владельцу. Фасадные записи функция не принимает.
- `meta/state-*` — сохранённые состояния, `meta/baseline-*` — именованные базовые версии. Экран не перезаписывает старые архивы. При сравнении берётся последнее сохранение не позднее конца выбранной даты в Москве. Отсутствие ранней истории показывается явно; готовность за прошлые даты не интерполируется. Непрерывность истории обеспечена для изменений через этот экран/RPC; сторонние прямые записи в таблицы должны сопровождаться снимком.
- Базовый план из MPP сохранён как `baseline-source`, исходное состояние — 12.11.2026. Сравнение отклонений на две даты выполняется относительно одной выбранной базы.
- Печать: светлая календарная таблица с повторяемой шапкой, A3/28 дней или A4/14 дней на блок. Строки и период соответствуют фильтрам и свёрнутым группам экрана. Для PDF используется системное окно печати браузера.
- Исходный MPP и его строки в репозиторий не включаются. `mockup-backend.sql` описывает только схему серверной функции и индекс.

Проверка: `node --test gpr/mockup-core.test.cjs gpr/links.test.cjs gpr/store.test.cjs`. Для дополнительной сверки исходника: `MOCKUP_FIXTURE=/private/source.json` (129 строк, 84 связи, 24 вехи, 119 совпадений окончания по календарю).

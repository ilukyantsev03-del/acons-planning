# Порядок загрузки данных в LIV

## Общий принцип

Любой внешний источник проходит этапы:

`файл → распознавание → сопоставление → предпросмотр → подтверждение → рабочая база`.

До подтверждения рабочие данные не изменяются.

## Этап 1. Организации, договоры и ключевые даты

Минимальные поля:

- подрядчик;
- номер договора;
- номер/наименование ключевой даты;
- договорная дата окончания.

Дополнительно LIV пытается определить:

- здание;
- блок/захватку;
- целевой объём;
- единицу измерения;
- тип номерных элементов.

Импортер должен обновлять существующую КД, а не создавать дубль.

## Этап 2. Версии графиков

Импортируются:

- ID задачи;
- родительская задача;
- название;
- уровень иерархии;
- длительность;
- текущие даты;
- базовые даты;
- процент из исходного графика;
- критичность;
- предшественники;
- тип связи и лаг;
- последователи;
- ответственный/подрядчик;
- объект и структура.

Новая загрузка создаёт тестовую версию. Только после проверки версия получает статус `accepted`.

## Этап 3. Фронты и проектные объёмы

Фронт определяется контекстом:

`здание + блок + этаж/ось/зона + работа`.

Подрядчик, даты и статус являются изменяемыми атрибутами и не должны создавать новый фронт при каждом изменении.

У фронта может быть несколько показателей:

- объём бетона, м³;
- кладка, м³;
- фасады/кровля, м²;
- воздуховоды/трубы, м.п.;
- оборудование, шт.;
- траншея, футляр, труба, засыпка и колодцы для наружных сетей.

Подробный BoQ не превращается автоматически в тысячи рабочих фронтов. Он хранится как справочная детализация и источник проектных объёмов.

## Этап 4. Реестр номерных элементов

До загрузки фактов по сваям, анкерам и другим номерным позициям создаются группы и плановые номера.

Контекст уникальности:

`проект + объект + тип + группа/марка + номер`.

Примеры:

- РЧВ / БНС-2 / №93;
- Дроп-оф / БСС-1 / №93;
- Главный корпус / грунтовые анкера / Г1 / №1;
- Главный корпус / грунтовые анкера / Г2 / №1.

Эти элементы не являются дублями.

## Этап 5. Ежедневные факты и ресурсы

Поддерживаемые события:

### Количественный факт

`дата + фронт/показатель + количество`.

### Номерной факт

`дата + конкретный элемент + статус Сделано`.

Повторный отчёт по уже выполненному номеру не увеличивает накопительный итог.

### Стадийный факт

Например `Разметка`, `Монтаж`, `Испытание` без обязательного количества.

### Ресурсы

- ИТР;
- рабочие;
- механизаторы;
- специализации;
- техника и количество.

### План подрядчика на следующий день

Сохраняется как плановое событие и не включается в фактическое выполнение.

## Правило накопительного факта

Дневные факты являются основным источником истины.

Если файл содержит одновременно дневные значения и накопительный итог:

- дневные значения импортируются как факты;
- накопительный итог используется для сверки;
- при расхождении создаётся конфликт, а история не переписывается автоматически.

## Прогноз ключевых дат

После связи КД с фронтом, показателем или группой элементов LIV рассчитывает:

- остаток;
- оставшиеся производственные дни;
- темп последних 7 дней;
- темп последних 28 дней;
- требуемый темп;
- прогноз к сроку;
- недобор;
- прогноз завершения.

Нулевые производственные дни входят в расчёт фактического темпа.

## Схемы

Схема не хранит самостоятельный параллельный факт. Отметка должна связываться с фронтом или номерным элементом. Тогда статус и готовность обновляются из основной базы.

## Отчёт Заказчику

Отчёт строится как срез на выбранную дату:

- общий объём;
- накопительный факт;
- факт на предыдущую отчётную дату;
- прирост;
- процент;
- схема;
- риски и комментарии.

После выпуска результат сохраняется в `report_snapshots`.

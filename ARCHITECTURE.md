# LIV Planning — архитектура

## Назначение

LIV Planning — единая система планирования, учета факта, ресурсов, ключевых дат, номерных элементов, схем и отчетности строительного проекта.

Основной принцип: данные хранятся один раз в нормализованной базе, а шахматка, Гант, план/факт, карточки организаций, схемы и отчеты являются представлениями одних и тех же сущностей.

## Источники

- Excel / CSV — табличный импорт.
- PDF — схемы и будущий анализ документов.
- Рабочие графики — отдельный тестовый контур с последующим принятием версии.
- Ежедневные отчеты подрядчиков — факты, люди, техника и план на следующий день.
- Ручной ввод — через единые карточки редактирования.

## Хранилища

- GitHub — код приложения и документация.
- Supabase PostgreSQL — рабочие данные.
- Supabase Storage — PDF и другие крупные файлы.
- IndexedDB / project_snapshot — переходный локальный кэш и резервная совместимость, не целевая рабочая база.

## Переход на нормализованную базу

До полного cutover действует двойная запись:
1. текущее состояние сохраняется в project_snapshot;
2. normalized-sync.js раскладывает данные по таблицам Supabase;
3. выполняется сверка количества ключевых сущностей;
4. после стабилизации экраны переводятся на чтение из нормализованных таблиц;
5. project_snapshot остается резервной копией.

## Совместная работа

Все изменяемые серверные сущности имеют row_version. Клиент хранит последнюю известную версию и не должен молча перезаписывать запись, которая уже была изменена другим пользователем.

## Источник истины для факта

Каноническая сущность факта — progress_facts.

factLog пока сохраняется только для обратной совместимости.

Типы факта:
- quantity — объем за период;
- cumulative_snapshot — накопительный снимок;
- status — стадийное событие;
- numbered_element — выполнение номерного элемента.

Накопительный итог, недельный прирост, остаток и процент должны рассчитываться из фактов, а не вводиться вручную как независимые значения.

## Ключевые даты

КД может быть связана с:
- подрядчиком;
- договором;
- зданием;
- видом работ;
- фронтом;
- задачей графика;
- целевым объемом и единицей измерения.

Для производственных КД рассчитывается прогноз риска на основании фактического темпа, остатка и даты окончания.

## Номерные элементы

Уникальность элемента определяется контекстом:
Проект + тип элемента + здание + группа/ярус/марка + захватка + зона + номер.

Одинаковый номер допустим в разных группах, например Г1 №7 и Г2 №7.

## Шахматки

Шахматка — отдельная сущность Matrix. Фронт может использоваться в нескольких шахматках через matrix_fronts.

Удаление представления не должно автоматически удалять общий фронт.

## Схемы

PDF хранится отдельно от отметок. Геометрия отметок хранится в относительных координатах.

Целевая модель:
- редакции;
- слои;
- точки;
- линии;
- полилинии;
- прямоугольники;
- полигоны;
- связь с фронтами и номерными элементами;
- история;
- экспорт отчетной схемы.

## Предтестовый контроль

Перед полноценным тестом приложение использует модуль preflight:
- проверка авторизации и роли;
- состояние нормализованной синхронизации;
- наличие обязательных модулей;
- доступность PDF-хранилища;
- сверка локальных и серверных данных;
- при ручном запуске — глубокая сверка идентификаторов.

Полный переход чтения с project_snapshot на нормализованные таблицы выполняется только после успешного тестового цикла. До этого snapshot остается страховочным источником чтения, а серверная модель работает параллельно.

## Отчётные снимки

Перед выпуском отчёта можно зафиксировать состояние на отчётную дату. Снимок хранит фильтры, фронты, показатели объёма, ключевые даты и номерные элементы. После выпуска такой снимок не должен пересчитываться задним числом при последующем исправлении исходных данных.

## PDF-схемы

Исходные PDF хранятся в приватном bucket liv-schemes. Storage key содержит только ASCII: schemes/<id>/source.pdf. Исходное имя файла хранится в метаданных. Процент отметки вручную не вводится: он рассчитывается только из связанного измеряемого фронта либо номерных элементов.

В карточке отметки выбираются фронт, группа и индивидуальный номерной элемент. Приоритет расчёта — выбранный элемент, затем группа с известным общим количеством, затем фронт. Для группы без общего количества готовность не рассчитывается. Открытие PDF пользователем без прав записи не сохраняет метаданные на сервер.

Версии строк клиента сохраняются независимо от номера выпуска JavaScript-модуля. Родительские связи графика записываются через ту же проверку row_version, что и задачи. Совпадение содержимого с сервером принимается без лишней записи и без повышения версии.

### Редактор схем: оформление и черновики

`schemes.js` хранит незаписанные фигуры и изменения оформления в `state.dirty`, отдельно от серверного снимка проекта. Кнопка «Сохранить рисунки» последовательно записывает отметки с контролем `row_version` и сохраняет проект. Черновик снимается только после успешного сохранения; при ошибке остаётся доступен для повтора. Карточка данных открывается отдельно от рисования. Оформление (`color`, `width`, `fill`) хранится в `appearance` отметки и в `scheme_marks.custom_data.appearance`; `color: null` означает цвет по статусу. Новые рисунки без связанных данных имеют `progressPercent: null`. Черновики живут до закрытия страницы (с предупреждением браузера); это не автосохранение.

### Единый расчёт факта

`js/fact-series.js` загружается до остальных модулей и объединяет дневные объёмы с накопительными отсечками. Его используют `core.js`, `import.js`, `milestone-risk.js` и `report-snapshots.js`. Возвращаются итог, дневные приращения для темпа и канонические строки для план/факта. Правила отражены в `IMPORT_RULES.md`; регрессии проверяют один и тот же набор фактов в рисках и отчёте.


### Редактор схем — 15.10.2026
PDF, PNG и JPEG хранятся в приватном `liv-schemes`, до 100 МБ, с ASCII-ключами `schemes/<id>/source.pdf|png|jpg`. MIME хранится в `schemes.mime_type` и снимке проекта. Изображение отображается как одна страница; координаты отметок нормализованы. Вставка скриншота через Ctrl+V доступна в разделе схем вне текстовых полей.

Перед рисованием задаётся обозначение. Оно хранится в `designation` и `scheme_marks.custom_data.designation` отдельно от статуса работ. Легенда текущей страницы строится из отметок с учётом фильтра, цвета, формы, толщины и заливки; одинаковые сочетания объединяются. Старые отметки без обозначения используют название/статус. Выбор из легенды повторно использует оформление. Заливка прямоугольников и кругов: 0/15/30/50/100%; линии без заливки, точки сплошные.

История до 100 действий за сессию: создание, оформление, обозначение и удаление рисунка. Отмена/повтор работают на текущей странице, в том числе после сохранения; версия записи берётся из актуального состояния. После отмены сохранённого действия требуется «Сохранить рисунки». История не сохраняется между перезагрузками. Карточка учётных данных сохраняется отдельно.

Удаление схемы остаётся окончательным с явным подтверждением. Оно выполняется в одной очереди с записью схемы. Перед удалением сверяются актуальные метаданные и применяется контроль текущего `row_version`; изменение технической версии не создаёт ложного конфликта. Изменённые другим пользователем метаданные блокируют удаление. Файл удаляется через Storage API после удаления строки; ошибка очистки файла не отменяет уже выполненное удаление строки.
